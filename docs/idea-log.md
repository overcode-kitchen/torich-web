# 아이디어 로그

> [!abstract] 이 문서의 성격
> 논의 중 튀어나온 아이디어를 **판정하지 않고 일단 적는 곳**이다.
> 채택 여부는 [direction-shift-plan.md](direction-shift-plan.md)의 Phase 2에서 정한다.
> 여기 적혀 있다고 만드는 게 아니고, 여기 없으면 잊혀진다.

각 항목은 **날짜 / 낸 사람 / 상태**를 단다.
상태: `아이디어` → `검토중` → `채택` / `보류` / `폐기`

## 2026-08-20 — 컨셉 논의에서 나온 것들

### ① 1억 베이스캠프 — 컨셉의 중심을 여기로

- 날짜: 2026-08-20 · 낸 사람: 김영문 · 상태: **확정 (8/20, Phase 1 결론)**

> "사람들이 1억을 어떻게 모으는지 그것을 보여주고 알려주는 **베이스캠프**가 되는 것이 제일 중요하다."

- 앱이 답해야 하는 질문이 **하나로 좁혀진다**: "나는 1억까지 얼마나 왔는가."
- 1억 달성 후에는 **"다음 1억"** 으로 카운터가 넘어간다. (상태: **채택 방향**)
- 지금 카피("매달 투자, 까먹지 않게")가 못 하던 **검색어 확보**가 여기서 생긴다 — "1억 모으기", "1억 통장", "종잣돈".
- **흩어진 적립 통합은 주기능이 아니라 수단이다.** 1억을 모으려면 흩어진 걸 봐야 하니 따라오는 것.
- **"목적 기반으로 모으는 걸 도와준다"는 폐기한다.** 우리가 시작한 지점이 맞지만, 그게 앱이 복잡해지고 한마디로 설명 안 되는 원인이었다.
- 상세: [direction-shift-plan.md](direction-shift-plan.md) Phase 1

### ② 목적 2층 구조는 화면에 올리지 않는다

- 날짜: 2026-08-20 · 낸 사람: 김영문 · 상태: **보류 (개념은 살리되 UI로 노출 안 함)**

> "기존 목적을 2층으로 내린다 — 나라도 그렇게 살리고 싶지만, 이걸 **화면에 띄우는 것 자체가** 사람들을 복잡하게 만들 것 같다."

- 판단: 1억(1층) 아래 기존 목적(2층)이라는 **데이터 구조는 타당하다.** 문제는 그걸 사용자에게 보여주는 순간 위계·소속·이동 개념을 전부 설명해야 한다는 것.
- 결론 방향: **구조는 내부에 두고, 첫 화면은 1억 하나만 말한다.** 목적별 보기는 진입 후 하위 레이어로.
- **합의(8/20)**: 한 줄로 설명이 안 되는 게 지금 문제의 뿌리다. 2층 구조는 **일단 그대로 두고, 핵심 위주로 개편한다.**
- 재논의 시점: Phase 2 화면 설계 (9/2~9/6).

### ③ 실시간으로 차오르는 적립 — 다람쥐가 도토리를 줍는다 ★

- 날짜: 2026-08-20 · 낸 사람: 김영문 · 상태: **아이디어 (강하게 살리고 싶음)**

> "매달 얼마를 모으는지를 기록했으면, **지금 실시간으로 얼마씩 차고 있는지**를 보여줄 수 있다. 정확한 팩트는 아니겠지만 얼추 맞을 거 아니냐. 다람쥐가 도토리를 줍는 것처럼 실시간으로 채워지는 걸 보여주면 재밌겠다."

- 원리: 월 적립액이 등록돼 있으면 **경과 시간 비례로 보간**해서 "지금 이 순간의 적립액"을 만들 수 있다. (월 100만 → 초당 약 0.38원)
- 가치: 저축은 **월 1회만 감정이 발생하는** 행위다. 이걸 **매 순간 발생하는 것으로 바꾼다.** 앱을 열 이유가 생긴다.
- 구현 갈래
  - **앱 내부**: 홈 상단 숫자가 미세하게 오르고, 토리가 도토리를 하나씩 물어 나른다. 웹만으로 가능.
  - **iOS 위젯**: 홈 화면 위젯. **Capacitor 로컬 번들 구조상 웹으로는 불가** — 네이티브 WidgetKit + App Group 공유 저장소가 필요한 별도 작업이다. 규모를 얕보면 안 된다.
- 반드시 처리할 것: **이건 실제 입금이 아니다.** "예상 적립 페이스" 같은 표기를 붙이지 않으면 사용자가 잔액으로 오해한다.
- 연관: [specs/99-acorn-physics-delight.md](specs/99-acorn-physics-delight.md) (도토리 물리 렌더가 이미 설계돼 있음 — 재사용 가능)

### ④ 1천만원 단위 돌파 시 — 도토리를 직접 문질러 색칠하는 세리머니 ★

- 날짜: 2026-08-20 · 낸 사람: 김영문 · 상태: **아이디어**

> "1천만원 단위가 바뀔 때마다 모달로 **직접 도토리를 그리거나 슥슥 문지르면 색칠되는** 재밌는 경험을 줘도 좋겠다."

- 1억까지 **마일스톤 10칸.** 각 칸이 도토리 1알이고, 돌파할 때마다 **사용자가 손으로 칠해서 채운다.**
- 왜 좋은가: 축하 모달은 보통 **읽고 닫는다**. 손으로 문지르게 하면 **행동이 남고**, 칠해진 도토리가 **컬렉션으로 누적**된다. 스크린샷을 찍어 공유할 물건이 생긴다 — 홍보 자산이기도 하다.
- 기술: canvas 마스크 + 터치 이동 경로로 지우기/칠하기. **모션 권한 불필요.** ③의 물리 렌더보다 훨씬 싸다.
- 주의: 이 인터랙션이 **1천만원마다 1번만** 발생한다는 건, 대부분의 사용자가 **평생 몇 번 못 본다**는 뜻이다. 단위를 낮추거나(100만/500만), 첫 진입에 맛보기를 줄 필요가 있다.

### ⑤ 주식 보유 주수(수량) 입력 — 필요하다

- 날짜: 2026-08-20 · 낸 사람: 선이 · 상태: **채택 방향 (설계는 Phase 2)**

- 지금 구조는 금액 중심이라 **"몇 주 갖고 있나"** 를 답하지 못한다.
- 다만 이건 **입력 필드 하나 추가로 끝나는 일이 아니다.** 평단가·소급 기록·평가금액 계산·기존 데이터 마이그레이션이 전부 딸려 온다.
- **급하게 정하지 않는다.** 다른 UX 플로우와 같이 놓고 본다. 바뀌어야 한다는 것만 확정.

### ⑥ 미국 시장 지원

- 날짜: 2026-08-20 · 낸 사람: 선이 · 상태: **채택 방향 (설계는 Phase 2)**

- 지금 "1억을 모은다"는 사람 중 상당수가 **S&P500·나스닥 ETF**로 모은다. 미국 종목이 안 되면 그 사람들의 실제 포트폴리오를 못 담는다.
- 딸려 오는 것: 환율, 시세 소스, 소수점 주수, 시장 구분(`market` 컬럼).
- 스키마 규칙 준수: **새 컬럼 추가 + `DEFAULT` 필수.** 기존 컬럼 건드리지 않는다. ([CLAUDE.md](../CLAUDE.md))

### ⑦ 온보딩에서 자산을 자동으로 불러온다 — 조회 API 리서치 필요 ★

- 날짜: 2026-08-20 · 낸 사람: 선이 · 상태: **리서치 대기 (담당: 김영문)**

> "내 자산이 얼마인지 불러오는 API가 있을 수도 있다. 온보딩에서 정확하지는 않아도 **이름으로 얼마 있는지 물어서** 자산을 알아올 수 있으면 확실히 정확하다. 그 기반으로 **금액만 수정**할 수 있게 해줘도 좋다."

- 왜 중요한가: ⑥에서 첫 질문이 **"지금 얼마나 모여 있나요?"** 로 바뀌는데, 이걸 **손으로 입력하게 하면 그 자리가 곧 첫 이탈 지점**이 된다. 자동으로 채워주고 **숫자만 고치게** 하면 온보딩 최대 난관이 사라진다.
- 리서치할 것 (아는 범위의 출발점 — **전부 검증 대상**)

  | 경로 | 성격 | 우리가 쓸 수 있나 |
  | --- | --- | --- |
  | **마이데이터(본인신용정보관리업)** | 금융위 **허가 사업자**만 가능 | 자본금·인력 요건이 있어 **개인 팀은 사실상 불가** |
  | **오픈뱅킹(금융결제원)** | 잔액·거래내역 조회 | 이용기관 등록 심사 필요. **가능성 검토 대상** |
  | **스크래핑 대행 API** (CODEF 등) | 사용자 인증서/간편인증으로 대신 조회 | **유료·종량 과금.** 현실적으로 제일 가까운 후보 |
  | 증권사 개별 Open API | 계좌 조회 | 증권사마다 제각각. 커버리지 문제 |

- **결정해야 할 것**: 비용 / 심사 기간 / 개인정보 처리방침·약관 개정 범위 / 실패 시 수기 입력 폴백.
- **기한**: 결과를 Phase 2 화면 설계(9/2~9/6) **시작 전까지** 받아야 온보딩 설계에 반영된다. → **8/29(금)까지 리서치 결과 공유.**
- 폴백은 반드시 남긴다: **연동이 안 되거나 사용자가 거부해도 수기 입력으로 온보딩이 끝나야 한다.**

### ⑧ iOS 홈 화면 위젯 — 네이티브로 별도 구현

- 날짜: 2026-08-20 · 낸 사람: 김영문 · 상태: **아이디어 (시점 미정, 언제 해도 됨)**

> "위젯은 iOS 앱으로만 하면 되니까."

- ③의 실시간 적립을 **앱을 안 열어도** 보게 만드는 물건. 홈 화면에서 도토리가 조금씩 차오른다.
- 구현 형태: **WidgetKit (Swift) + App Group 공유 저장소.** 웹 번들과 분리된 네이티브 타깃이다.
  - 웹(WebView)이 계산한 값을 App Group `UserDefaults`에 써두면, 위젯이 그걸 읽어 렌더한다.
  - 위젯은 **상시 갱신되지 않는다** — iOS가 타임라인을 스케줄링하므로 "초 단위로 오르는 애니메이션"은 불가. **타임라인 엔트리를 시간 단위로 미리 계산해 넣는** 방식이 된다.
- 전제: 실시간 보간(③)이 앱 안에서 먼저 성립해야 위젯에 얹을 값이 생긴다. **③ → ⑧ 순서.**
- 독립적이라 **v2.0.0 이후 아무 때나 붙일 수 있다.** 로드맵을 막지 않는다.

## 진행 방식에 대한 합의 (2026-08-20)

> [!important] 화면은 선이가 다시 그린다
> 그래서 이 세션의 산출물은 **UI 시안이 아니다.** 화면마다 아래 4개를 정의하는 게 산출물이다.
>
> 1. **이 화면이 사용자에게 답해주는 질문 1개**
> 2. **여기서 할 수 있는 행동**
> 3. **이 화면이 들고 있어야 하는 정보**
> 4. **들어오는 경로 / 나가는 경로**

> [!important] 온보딩부터 다시 짠다
> 컨셉이 "1억 베이스캠프"로 바뀌면 **첫 가입 직후에 묻는 것도 달라져야 한다.**
> 지금은 "목적을 만들고 → 적립 항목을 붙인다" 순서인데, 1억이 기본 목표라면 **목적 생성이 첫 관문일 이유가 없다.**
> 첫 질문은 "무엇을 위해 모으나요?"가 아니라 **"지금 얼마나 모여 있나요?"** 가 된다.
