## 1. 기능 존치 / 삭제 판정 — **완료**

판정 기준은 하나 — **"1억 모으기를 돕는가."**

- [x] **목적(goals)** — **삭제.** 목표가 1억 하나면 계층이 사라진다. **태그로도 남기지 않는다**
- [x] **목적 프리셋** — **삭제.** 목적에 종속
- [x] **토리 키우기** — **삭제.** 진입 경로가 없어 이미 없는 기능. 브랜드 스토리 파일과 **분리해서** 지운다
- [x] **소급 기록** — **존치.** 과거 회차를 넣을 수 있게 한다
- [x] **알림 7종** — **v2.0.0에서 손대지 않는다.** 문구만 1억 기준으로 고친다
- [x] **FAQ · 브랜드 스토리** — **존치 · 내용 교체.** 지금 내용이 목적·3유형 기준이라 재작성이 필요하다
- [x] **`/design-system`** — **존치.** 컴포넌트·토큰 점검용으로 실제로 쓴다
- [x] **통계 23섹션** — **`/detail` 3섹션으로 축소.** 단 재작성이라 **순서는 맨 뒤** (§4에 종속)
- [x] **납입 연기** — **삭제** **(확정)**. 마감일이 없어 "빠뜨림"이 사라지고,
      못 넣은 달은 **소급으로 채우면 된다.** 23개 파일이 통째로 빠진다
- [x] **연속 기록 → 누적으로 바꾼다** **(확정)**
      `"3개월 연속"`은 한 달만 걸러도 **0으로 리셋**되어, 다섯 번 넣은 사람에게 "1개월"이라고 말한다.
      **정의상 못 채운 달을 벌주는 장치**라 "혼내지 않는다"는 원칙과 정면으로 어긋난다.
      → `"여섯 번째 달"` (총 채운 달 수). **절대 줄어들지 않는다.**
      공유 카드 문구(§8 브리프)도 이미 이 형태로 써 두었다
- [x] **적립 항목 상세 화면** — **삭제** **(8/25 확정)**.
      카운터·홈 목록·`/detail`이 답을 다 갖고 있어 **한 항목만 따로 볼 이유가 없다.**
      **숨기지 않고 뺀다** — 고치기는 `/add?editId=`로 직행, 빈 달 메우기는 기록 탭이 받는다.
      → 아래 §4의 *"항목 상세의 건너뜀 표기"* 항목은 **화면 자체가 사라져 무효**가 됐다
- [x] **홈의 "이번 달 할 일" 체크** — **자동 채움으로 대체** **(8/25 확정)**.
      사용자가 누르는 체크는 숙제다. **납입일이 지나면 채워진 것으로 보고, 틀렸을 때만 내린다.**
      → 구현 방식은 미정 (§6 스키마 결정 3건)
- [x] **실시간 카운트업 · 위젯** — **v2 범위로 올린다** **(8/25 확정)**.
      제외했던 이유는 비용이었는데, **정합성을 포기하면서 비용이 내려갔다** (`계획액 ÷ 초`, 네트워크 불필요).
      **네이티브(WidgetKit + App Group) 전환만 장기 과제로 남긴다** — v2 검증은 웹뷰에서
- [x] **ETF(종목·주수)** — **유지 확정** **(8/25 재확인)**. 빼지 않는다
- [ ] `/notifications?demo=1` — 개발용 경로 정리

## 2. 입력 플로우

**8/24 확정**

- [x] **입력 화면 레퍼런스를 은행 적금 상세 페이지로 바꾼다** **(8/25 확정 · 8/24판 뒤집음)**
      기존은 토스식 **"한 화면에 한 질문"**이었는데, 적립 항목은 **금액·주기·시작일이 서로 물려 있어서**
      하나를 정하면 앞엣것을 다시 보고 싶어진다. 화면이 나뉘면 그때부터 **위아래로 헤맨다.**
      → **한 화면에서 위→아래로 읽으며 자연스럽게 채워지는 폼**으로 간다.
      답한 만큼만 아래가 열리고(progressive disclosure), 고칠 것은 스크롤만 올리면 거기 있다.
      - 참고: 현재 코드는 이미 A/B/C 그룹 스크롤 구조다 (`app/hooks/investment/add/useAddItemFlow.ts`).
        **뒤집는 쪽이 구현도 더 싸다**
- [x] **유형(투자/예적금/현금) 질문 삭제** — 입력 규칙 하나로 통일
- [x] **종목 검색 · 주수 존치** — ETF는 **주 단위로 사는 물건**이라 금액만으로는 기억이 안 된다
- [x] **금리 · 만기일은 선택 필드** — 안 물어도 되게만 만들고 지우지는 않는다

**남은 것**

- [x] **⭐ 1억 카운터는 원금 2층이다** **(8/25 확정 · 8/24판 3층을 뒤집음)**

      | 층 | 무엇 | 누가 정하나 | 줄어드나 |
      | --- | --- | --- | --- |
      | **① 1억 카운터** | **넣은 돈(원금).** 체결 시점 실제 금액의 합 | 나 | **안 줄어든다** |
      | **② 도토리 · 완주** | **납입 횟수만** 본다. 시세와 무관 | 내 행동 | 안 줄어든다 |
      | (보조) 시세 | 항목 목록의 보조 표기로만. **카운터에 섞지 않는다** | 시장 | — |

      **뒤집은 이유는 "정합성을 신경 쓰지 않는다"였다.** 카운터에서 시세를 빼면
      카운트업이 **결정적**이 되어 시세·환율·네트워크 없이 계산되고, **위젯이 오프라인에서도 같은 값**을 그린다.
      **축하는 내가 통제한 것에만 붙인다**는 원칙이 도토리를 넘어 카운터 전체로 확장되고,
      카운터가 절대 줄지 않아 **"혼내지 않는다"** 원칙과도 맞는다.
      → 감수하는 것: 주식이 오른 사람은 실제 자산보다 낮게 보인다.
      → 시세 인프라(`app/api/stock/route.ts`, `app/utils/stock-price-fetcher.ts`)는 **지우지 않고 보조 표기로 남긴다**
- [x] **1억에 "목표 시점"을 선택으로 둔다** **(확정)**
      **마감일이 아니라 페이스 계산기의 입력값이다.** `매달 얼마` ↔ `언제까지` 는 같은 식의 양변이라
      **온보딩에서 둘 중 하나만 받으면 나머지가 계산된다.**
      - 안 정하면 → 앱이 **도착일**을 예측해서 말한다 (기본)
      - 정하면 → **필요 월 적립액**을 말한다
      - **D-day · 빨간 미달 표시는 만들지 않는다.** 못 지켜도 아무 일이 안 일어나고
        **"5개월 밀렸어요"까지만** 회색으로 말한다. 강제성 0
- [x] ~~**미국 종목 환율은 체결 시점 값을 저장한다**~~ → **환율 컬럼은 만들지 않는다** **(8/25 확정)**
      원금 2층 + `payment_history.amount`(원화)로 정해지면서 **환율을 따로 저장할 이유가 사라졌다.**
      체결 시점 **원화 금액 하나**만 박으면 과거 기록이 환율에 흔들리지 않는다. **환율 조회 API를 새로 만들 필요도 없다**
- [x] **만기일은 묻지 않는다** **(확정)**
      유형을 없애 **적금인지 ETF인지 앱이 모르므로**, 물으려면 모두에게 물어야 하는데 그건 혼란만 준다.
      **도달 예측을 최근 3개월 실제 납입 평균으로 계산하면 만기를 몰라도 자동으로 따라잡는다**
      (적금이 끝나면 납입액이 줄고 → 3개월 평균이 내려가고 → 도착일이 밀린다. 3개월 늦게 반영될 뿐).
      만기가 오면 **"적금이 끝났어요" 알림 한 번**으로 대신한다
- [x] **소급은 기간 제한 없이 받되, 넣어도 총액은 변하지 않는다** **(확정)**
      2년 전이든 5년 전이든 다 넣을 수 있다. **기록의 디테일만 올라가고 1억 카운터는 1%도 안 움직인다**
      — 시작 잔액에서 그만큼 옮겨 담는다. 채워지는 것은 **캘린더 · 월별 그래프**다
      - [ ] 소급 합이 **시작 잔액을 넘으면** → **총액을 올린다**(추천). 상세 기록이 어림수보다 정확하다
- [x] **주수 · 시장이 붙어도 "필수 4개"가 안 깨진다** **(검증됨)**
      종목을 고르면 **이름이 자동으로 채워져 오히려 하나 줄고**, 주수는 "매달 얼마"가 "매달 몇 주"로
      바뀔 뿐이며, 시장은 종목에 붙어 있어 **묻지 않는다**
- [x] **원/주 토글은 금액 입력 화면에 둔다** **(확정)** — `300,000 [ 원 | 주 ]`. 탭 1회 추가
- [ ] 적립 항목 1개 추가에 드는 **동작 수를 숫자로 확정** (지금 안: 타이핑 2 + 탭 4)

## 3. 자산 불러오기 (스크린샷)

> [!note] 기존 5개 질문은 **금융 연동 전제**로 쓴 것이라 폐기했다
> 연동은 사업자 자격이 없어 불가능하고(브리프 §5), 방식이 **스크린샷 + 비전 모델**로 바뀌었다.
> 그래서 "자동 재조회 여부" · "연결 인증 만료 알림" 같은 질문은 **성립하지 않는다.**
> "금액이 줄었을 때 카운터를 내릴 것인가"는 **3층 구조에서 이미 답이 나왔다 — ①은 원래 줄어든다.**

> [!success] **v2.0.0 필수 기능이다.** 범위 축소 후보가 아니다
> **단 8/25부터 "A(이미 모으는 사람) 경로에서 필수"로 뜻을 좁힌다.**
> B(처음 모으는 사람)에게는 불러올 자산이 없어 **스크린샷 단계가 아예 없다** (브리프 §4).

> [!note] 스샷을 안 쓰는 경우는 전부 **"직접 타이핑"으로 흡수한다** **(8/25 확정)**
> 개인정보가 걱정돼서든, 못 읽어서든, 항목이 서너 개뿐이라 손이 더 빠르든 마찬가지다.
> **각각을 위한 별도 예외 화면·특별 처리를 만들지 않는다.** 갈래가 늘면 만드는 사람부터 헷갈린다.

- [ ] **실패율을 잰다** — 우리 둘 화면 10장. 이 숫자가 있어야 "읽기 애매함" 표시와 재시도 흐름을 설계한다
- [ ] **개인정보 처리방침 개정** — 이미지 업로드와 외부 처리 위탁이 새로 생긴다 (심사 전 필수)
- [ ] 읽어온 항목과 수기 항목이 **같은 계좌**일 때 중복을 어떻게 잡는가 (안 잡으면 1억이 두 배로 뻥튀기된다)
- [ ] 비전 모델 **비용 상한**과 남용 방지 (1인 1일 N장)
- [ ] 읽어온 금액을 **시작 잔액에 넣는가, 적립 항목으로 만드는가** (둘 다면 §2의 총액 불변 규칙을 탄다)

## 4. 화면 내용

- [ ] **`/detail` 3섹션의 정확한 내용** — 자산 추이는 **원금으로 그린다**(카운터 2층 확정에 따라). 나머지 2섹션이 미정
- [ ] **지난 달 소급 체크**를 허용할 것인가 — 되면 정직한 기록, 안 되면 숫자가 굳는다
- [x] **도달 예측은 온보딩 계획으로 계산한다** **(확정)**
      실제 납입 평균으로 예측을 낮추지 않는다 — 그러면 **내가 정한 목표가 나도 모르게 깎인다.**
      계획을 바꾸는 건 사용자뿐이고 앱은 권하기만 한다. **계획을 건너뛴 사람은 항목 합계가 곧 계획**이다
- [x] **어긋날 때는 계획 수정을 권한다** **(확정)**
      **계획의 20% 이상이 3개월 연속** 어긋났을 때만. 매달 물으면 잔소리가 된다.
      **더 넣는 쪽도 본다**("계획을 올릴까요?"). 항목이 만기로 끝나 계획에 구멍이 나도 같은 방식으로 묻는다
- [x] **항목 담기 화면에 계획 채움 표시를 넣는다** **(확정)** — `100만원 중 60만원 채움 · 40만원 남음`
- [x] ~~항목 상세의 **"건너뜀" 표기는 없앤다**~~ — **무효** **(8/25)**. 항목 상세 화면 자체를 삭제했다 (§1)
- [x] **온보딩을 유저 타입으로 분기한다** **(8/25 확정)**
      로그인 직후 **"처음 모으시나요 / 이미 모으고 계신가요"** 한 번만 묻는다.
      **A** = 시작 잔액(스샷/타이핑) → 계획 → 홈 30% · **B** = 계획만 → 홈 0%.
      **갈라지는 것은 온보딩뿐이고 홈·기록·설정은 같은 화면**이다
- [x] **B는 계획(월 X원 + 납입일)만으로 홈이 돌아야 한다** **(8/25 확정)**
      0원부터의 진행률 · 예상 달성 시점 · 위젯 카운트업이 **전부 계획액 하나로 계산된다.**
      **데이터가 없다고 앱이 빈 껍데기가 되면 안 된다**
      - [x] 전제 검증: **적립 항목이 상품 연결·잔액 없이 계획만으로 존재할 수 있는가** → **가능.**
            `records`의 실질 필수값은 이름·금액·주기뿐이고 종목·시장·만기일·금리는 전부 비울 수 있다.
            (`app/hooks/investment/add/useSavingsCashSubmit.ts`가 이미 `annual_rate: 0, final_amount: 0`으로 넣는다)
            **스키마 변경 없이 되는 항목이다**
- [x] **자동 체크가 기본이다** **(8/25 확정)**
      사용자가 들어와 직접 누르는 구조가 아니라 **이미 채워져 있는 구조**.
      예적금 자동이체 항목은 **납입일이 되면 자동으로 채워졌다고 간주**한다.
      **사용자가 하는 일은 틀렸을 때 내리는 것뿐**이고, 내리는 UI는 회색·무표정으로 둔다
      — "안 넣으셨네요"가 아니라 **"이번 달은 빼둘게요"**
      - [x] **B도 A와 똑같이 채운다** **(8/25 확정)** — 실제로 안 넣었으면 내리면 된다
      - [x] **구현은 가상 채움 + `skipped` 예외 행** **(8/25 확정)** → §6-C
- [x] **위젯을 강화한다 — %가 아니라 금액(원)이 오르는 실시간 카운트업** **(8/25 확정)**
      **정합성은 신경 쓰지 않는다.** 정확한 평가금액도 수익률도 아니고,
      목적은 **"지금 모으는 중, 올라가는 중"** 하나다
      - [x] **v2 범위는 앱 안의 카운트업까지** **(8/25 확정)**.

### 8/25 회의로 정한 스키마 변경 — **4건 전부 확정**

전부 **유저당 1행**이고 `user_settings`가 이미 1:1이라 **조회가 늘지 않는다.** 새 테이블은 만들지 않는다.

#### B. 회차별 납입 금액 → `payment_history.amount` **(확정)**

**현황** — 금액 컬럼이 없어 이렇게 역산한다.

| 모드 | 지금 |
| --- | --- |
| **주수 모드** | `captured_shares × captured_price` → 확정값 |
| **금액 모드** | **저장 안 됨.** 현재의 `record.monthly_amount`로 폴백 (`app/utils/realized-principal.ts`) |

> 그래서 월 납입액을 30만 → 50만으로 고치면 **과거 30만원 회차가 전부 50만원으로 소급 변경된다.**
> **원금이 카운터가 되는 이상 이건 그대로 카운터 오차다.**

| 컬럼 | 타입 | DEFAULT | 뜻 |
| --- | --- | --- | --- |
| `amount` | `bigint` | `NULL` | **체결 시점 실제 납입액(원)**. NULL이면 기존 폴백 그대로 |

**환율은 원화로 흡수한다** **(확정)** — `amount`에 원화를 박으므로 `fx_rate` 컬럼도, 환율 조회 API도 만들지 않는다.
기존 데이터는 NULL이라 **현행 폴백이 그대로 돌아간다** (마이그레이션 불필요).

- [ ] 마이그레이션 작성 + 체크 시점에 `amount` 채우는 코드 (`app/utils/payment-history-db.ts`)

#### C. 자동 채움 → **가상 채움 + `skipped` 예외 행** **(확정)**

**채운 기록을 만들지 않는다.** 납입일이 지났으면 **계산할 때 채워진 것으로 본다.**
서버 cron 방식은 쓰지 않는다 — 중복 방지·타임존을 떠안고, **한 번 만들어진 기록은 되돌리기 어렵다.**

**기록이 남는 것은 예외뿐이다.**

| 컬럼 | 타입 | DEFAULT | 뜻 |
| --- | --- | --- | --- |
| `is_skipped` | `boolean` | `false` | 사용자가 "이번 달은 안 넣었어요"로 **내린 달에만** 행이 생긴다 |

**평소에는 행이 0개다.** 화면에서는 회색·무표정으로만 보인다 — *"이번 달은 빼둘게요"*.

- [x] **B(처음 모으는 사람)도 A와 똑같이 채운다** **(확정)** — 실제로 안 넣었으면 내리면 된다.
      *"정합성은 신경 쓰지 않는다"*는 결정과 일관되고, **B에게만 예외 흐름을 만들지 않는다**
- [ ] 소급 기록 · `is_retroactive`와 `is_skipped`가 겹칠 때의 규칙 정리

#### D. `record_type` → **종목 유무로 자동 판정** **(확정)**

유형 질문은 없앴지만 `records.record_type`은 NOT NULL(`DEFAULT 'investment'`)이다.
**종목을 고르면 `investment`, 안 고르면 `cash`**로 앱이 알아서 채운다.
사용자에게는 아무것도 묻지 않으므로 *"유형을 먼저 묻지 않는다"*와 어긋나지 않고,
구버전 앱이 이 값을 읽어도 지금과 똑같이 동작한다.
