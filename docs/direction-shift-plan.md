# 토리치 방향성 전환 실행 계획

> [!abstract] 한 줄 요약
> **"기능을 더 만드는 것"을 멈추고, "사람이 찾아올 이유"를 먼저 만든다.**
> 컨셉을 하나로 좁히고 → 앱을 그 컨셉에 맞게 정리하고 → 측정 가능한 상태로 배포한다.
> **홍보는 위 세 가지가 끝난 뒤 별도 계획으로 잡는다.**

> [!danger] 이 문서의 성격
> 이 문서는 **결정된 내용을 적는 문서가 아니라, 무엇을 언제 어디서 결정할지를 적는 문서다.**
> 컨셉 선택, 기능 취사선택, 판단 기준 수치 등 실제 의사결정은 **레포에 접근 가능한 Claude Code 세션에서 코드와 데이터를 직접 뜯어보며** 진행한다.
> 이 문서에서 미리 답을 정해두지 않는다.

## 0. 왜 이 계획이 필요한가

### 지금 상태

| 항목 | 현실 |
| --- | --- |
| 개발 기간 | 1.0.0 → 1.4.0, 수 개월 |
| 앱스토어 노출 | **월 1회** |
| 홍보 | 0회 |
| 메인 카피 | "매달 투자, 까먹지 않게" |
| 기능 구조 | 투자/예적금/현금 3분기 + 각기 다른 입력 규칙 |

### 진단

> [!warning] ① 한 번도 세상에 내놓은 적이 없다
> 앱스토어 배포 ≠ 출시. 쓰레드, 인스타, 바이브코딩 커뮤니티, 투자 커뮤니티 어디에도 알린 적이 없다.

> [!warning] ② 카피가 차별점이 아니다
> "매달 투자, 까먹지 않게"는 캘린더 알림·메모·토스 알림으로도 해결되는 문제다. **토리치여야 할 이유가 카피에 없다.**

> [!warning] ③ 검색어가 없다
> 사용자는 "필요 → 앱스토어 검색 → 설치" 순서로 움직인다. 무신사에서 바지 살 때 "바지"를 치는 것처럼.
> **토리치는 뭐라고 쳐야 나오는가?** 이 질문에 우리 둘 다 답을 못 한다. 노출 월 1회는 그 결과다.

> [!warning] ④ 입력 플로우가 사용자에게 헷갈린다 (선이 지적)
> - 투자/예적금/현금으로 나뉜 뒤, **종류마다 입력해야 하는 것이 다르다**
> - 어떤 건 만기일을 넣어야 하고, 어떤 건 소급 기록이 되고, 어떤 건 시작일을 정한다
> - **목적의 기간을 넘어가는 만기일**을 어떻게 처리해야 하는지 규칙이 불명확하다
> - 만드는 사람도 헷갈리는 플로우를 처음 온 사용자가 이해할 리 없다
>
> → 이건 **UX 기획과 UI로 풀어야 할 문제**다. (둘 다 동의)

### 대체 불가능한 우리 자산

1. 흩어진 적립을 **한 화면에서 보는 통합 현황**
2. **목적 기반 진척률**과 거기서 오는 성취감

- [x] 실제 의사결정은 **레포를 볼 수 있는 환경(Claude Code)** 에서 한다.

## Phase 1. 컨셉/포지셔닝 확정 ★ — **완료 (8/20)**

> 기간: 8/19 ~ 8/20 (당초 8/22까지, **이틀 앞당겨 종료**)

### 확정 사항

> [!success] 주기능은 **"1억 모으기"** 하나다
> 흩어진 적립을 한 화면에서 보는 것은 **주기능이 아니라 수단**이다.
> 1억을 모으려면 여기저기 흩어진 걸 모아 봐야 하니까 자연히 따라오는 것이지, 그 자체가 앱의 이유가 아니다.

| 항목 | 확정 |
| --- | --- |
| **주기능 1개** | **1억 모으기.** 사용자가 1억까지 얼마나 왔는지 보여주고, 어떻게 모으는지 알려주는 **베이스캠프** |
| **타겟 1문장** | **"1억을 모으려는 사람이 쓰는 앱"** |
| **메인 타겟 (1차)** | **이미 1억 모으는 방법을 갖췄고, 우리 걸로 기록하려는 사람.** 가르치는 게 아니라 **빨리 옮겨 담게** 한다 ([idea-log ⑨](idea-log.md)) |
| **2차 타겟** | 이제 시작하려는 사람. 방법 제시·프리셋이 필요. **1차를 먼저 만든 뒤 붙인다** |
| **버리는 컨셉** | **"목적 기반으로 모으는 걸 도와준다"** — 시작점은 이거였지만, 이 컨셉이 곧 앱이 복잡하고 한마디로 설명 안 되는 원인이었다. 그래서 1억으로 바꾼 것이다 |
| **한 줄 카피** | **미정 — 의도적으로 미룬다.** 화면·구조가 확정된 뒤에 쓴다(선이 판단, 8/20). 구조가 흔들리는 상태에서 쓴 카피는 구조가 바뀌면 같이 버려진다. → **Phase 2 종료(9/6) 직후** |
| 키워드 | 아래 제안, **김영문 확인 대기** |

### 왜 키워드 30개 실측을 하지 않았나

당초 계획은 "8/20에 둘이 1시간, 키워드 30개를 앱스토어에 다 쳐보고 상위 5개 앱을 캡처한다"였다. **취소했다.**

- **"1억 모으기" 앱은 사실상 1개뿐이다.** 경쟁 밀도를 조사할 밀도 자체가 없다.
- 우리가 낄 자리를 찾는 조사가 아니라, **자리가 비어 있다는 걸 이미 아는 상태**다.
- 스퍼트 기간에 확인된 사실을 재확인하는 데 쓸 시간이 없다.

→ **8/21 Claude Code 컨셉 판정 세션도 함께 취소한다.** 판정할 것이 남지 않았다.

### 키워드 안 (Claude 제안 · 실측 데이터 없는 가설 · 확인 대기)

**주력 3개**

| 키워드 | 근거 |
| --- | --- |
| **1억모으기** | 우리가 먹으러 가는 자리. 경쟁 1개 |
| **목돈모으기** | "1억"을 안 떠올린 사람이 치는 말. 유입 폭이 제일 넓다 |
| **재테크** | 20~30대가 실제로 치는 말. 볼륨이 가장 크다 |

**보조 7개** — 목돈 · 자산관리 · 저축 · 적금계산기 · 돈모으기 · 저축목표 · 투자기록

> [!warning] **"종잣돈"은 쓰지 않는다**
> 타겟인 20~30대가 실생활에서 쓰지 않는 말이다. 검색창에 치지 않는 단어는 키워드가 아니다.
> 같은 자리를 노린다면 **목돈 · 목돈모으기 · 재테크 · 자산관리**로 간다.

**앱스토어 필드 안**

| 필드 | 안 |
| --- | --- |
| 앱 이름 (30자) | `토리치 - 1억 모으기` |
| 부제 (30자) | `흩어진 적금·투자를 한 곳에` |
| 키워드 (100자) | `목돈,목돈모으기,재테크,자산관리,저축,돈모으기,저축목표,투자기록,모으기,1억,통장,만들기,파이어족,가계부,자산,포트폴리오,목표저축,계산기,월급,비상금,예금,적금이자` (91자) |

> [!note] 필드 작성 규칙
> - **이름·부제에 쓴 단어는 키워드 필드에 중복해서 넣지 않는다.** 자리 낭비다
> - 쉼표만 쓰고 **띄어쓰기는 넣지 않는다.** 공백도 100자에 포함된다
> - 한국어는 애플의 단어 조합이 약한 편이라 복합어를 통째로 넣었다 — **이건 검증 대상이다**
>
> 실제 반영은 Phase 4(ASO)에서 한다.

## Phase 2. 기능 취사선택 & 플로우 재설계

> 기간: 8/25 ~ 9/6 (2주)
> 진행 환경: **Claude Code (레포 직접 접근)**

> [!important] 이건 코드 리팩토링이 아니라 UX 기획 작업이다
> 화면과 플로우를 실제로 보면서, 사용자가 어디서 멈추는지를 기준으로 판단한다. 결과물은 **재설계된 플로우**여야 한다.

### 풀어야 할 문제 (선이 지적, 원문 기반)

1. **투자/예적금/현금 3분류** — 이 구분이 사용자에게 의미가 있는가?
2. **종류마다 다른 입력 규칙** — 어떤 건 만기일, 어떤 건 소급 기록, 어떤 건 시작일. 왜 다른가?
3. **목적 기간을 넘어가는 만기일** — 이 케이스를 어떻게 정의할 것인가? 지금은 규칙이 없다
4. **입력 플로우 자체의 복잡도** — 목적 만들고 적립 수단 붙이는 과정이 몇 단계인가, 몇 단계여야 하는가
5. **가지가 여기저기 붙은 구조** — "최소화로 만들고 거기서 뻗어야 하는데, 우리는 가지를 만들어서 한 나무에 갖다 붙인 느낌"

### 기능 취사선택 원칙

> [!warning] 서랍에 넣지 않는다
> 없앨 기능은 **없앤다.** "일단 숨겨두자", "상세 설정으로 접자"는 문제를 미루는 것이지 푸는 게 아니다.
> 각 기능마다 던질 질문은 **"이게 왜 필요한가"** 이지 **"어디에 둘 것인가"** 가 아니다.
> 기능이 필요하다면 눈에 잘 보이는 자리에 있어야 하고, 필요 없다면 코드에서 지운다.

## 3. GA 정비 — 지금 할 일

> [!important] GA는 새로 붙이는 게 아니라 **이미 붙어 있다**

> **4월 말부터 데이터가 쌓이고 있는데 콘솔을 한 번도 열지 않았을 뿐이다.**
> 그래서 이 항목은 Phase 4가 아니라 **Phase 0(지금)** 으로 당겼다.

### 속성 2개

| 속성 | 측정 ID | 들어가는 것 |
| --- | --- | --- |
| Torich **Prod** | `G-SC1LBTD65X` | `torich.vercel.app` + **앱스토어 iOS 빌드** |
| Torich **Dev** | `G-C8E4VZ883Y` | `localhost` + Vercel Preview |

**볼 것은 Prod다.** 콘솔 좌측 상단 속성 선택기에서 매번 확인한다.

### 문제 — 우리 둘의 트래픽이 실사용자 데이터에 섞인다

사용자가 적을 때 **우리 둘이 곧 통계의 대부분**이 된다. 우리는 만든 사람이라 이동 경로가 일반 사용자와 완전히 다르고, 이 상태의 숫자로는 아무 판단도 할 수 없다.

**"개발용은 Dev 속성으로 간다"로는 해결되지 않는다.** 우리가 폰에 깔아 쓰는 건 **앱스토어 정식 빌드**라서 Prod로 들어간다.

### 해결 — 3단계

| 단계 | 내용 | 담당 | 시점 |
| --- | --- | --- | --- |
| ① | 로그인한 사용자가 **우리 둘이면 이벤트에 `traffic_type: internal` 을 붙여서** 보낸다. 판별은 Supabase user.id 목록(환경변수)으로 한다 (**#264**, v1.5.0) | Claude Code | Phase 0~2 |
| ② | GA 콘솔 → 관리 → 데이터 설정 → **데이터 필터**에서 `internal` 제외 필터를 만들고 **"테스트" 모드**로 둔다 | 김영문 | ① 배포 후 |
| ③ | 우리 트래픽이 실제로 걸리는지 확인한 뒤 **"활성"으로 전환** | 김영문 | Phase 4 |

> [!warning] 데이터 필터는 소급 적용되지 않는다
> **활성으로 켠 시점 이후 데이터만** 걸러지고, 걸러진 데이터는 **영구적으로 복구할 수 없다.** 그래서 ②에서 반드시 테스트 모드를 거친다.
> 그리고 **4월~지금까지 쌓인 과거 데이터에는 이 필터를 적용할 수 없다.** 과거분에서 우리 둘을 빼고 보려면 콘솔의 **탐색(Exploration)** 에서 세그먼트로 제외해야 한다.

> [!note] IP 기반 "내부 트래픽 제외"는 쓰지 않는다
> GA가 기본 제공하는 방식은 IP 주소 기반인데, 폰은 LTE·와이파이를 오가며 IP가 계속 바뀌어서 **모바일에서는 사실상 안 걸린다.** 그래서 로그인 계정 기준(①)으로 간다.

### 지금 GA에서 확인할 것 → [docs/ga4-console-guide.md](ga4-console-guide.md)
